Lab 3: Keypad Scanner with Two Digit Display

The SystemVerilog implementation and simulation of a keypad scanner which reads user inputs from a 4x4 matrix keypad and displays them to a 2-digit display.

Design and Testing Methodology

This design uses largely the same physical circuit from lab 2, except for the introduction of a 4x4 matrix keypad as input to the FPGA instead of the input switches. Additionally, two PNP transistors were used for sourcing current to the 2-digit display.

The SystemVerilog HDL was designed to scan and properly debounce user inputs from the keypad. The keypad is scanned using the scanner_fsm finite state machine, asynchronous user input is synchronized, the keypad value is decoded as a binary value intelligible to the two_dig_display, the two values to be displayed are stored in the digit_mem finite state machine, which finally sends those two values to the two_dig_display. scanner_fsm instantiates two sub-fsm’s, debouncer and col_fsm. col_fsm scans the keypad column-by-column, while debouncer makes sure that user inputs are legitimate presses (anti-ghosting) and that the input has settled to its high value. When the button is released, the low state is similarly debounced to prevent a false keypress.

Technical Documentation

The source code for the project can be found in my E155 GitHub repository under “lab3_keypad.”

Block Diagram

The block diagram in Figure 1 shows the lab3_ll_keypad top module, and the synchronizer, scanner, keypad_decoder, digit_mem, and two_dig_display submodules.

keypad_decoder is simply combinational logic while digit_mem is a finite state machine as explained in the following section. See lab 2 for the two_dig_display block diagram.

FSM Diagrams

The above finite state machine diagrams show how the scanner, col_fsm, and digit_mem submodules work.

The scanner scans a column on the keypad, waits 10 clock pulses to ensure the synchronizer has processed any user inputs, reads the value, if it is a legitimate input it is debounced, and then turns on until the input changes. Then it is debounced again and begins scanning again. Additionally, an error checker is used for debugging and resetting the scanner if there is a false input.

col_fsm simply scans one column at a time.

digit_mem idles until the keypad_decoder sends it a valid keypress value, which stores the new value as the first digit and discards the old second digit. Then it stays in the ON state until the key is no longer being pressed.

Results and Discussion

The keypad scanner functioned as I expected in simulation, although hardware debugging revealed oversights in my simulation which I later corrected, chiefly the error state in my scanner submodule was causing me grief.

The hardware implementation works! Keypresses are registered on the two segment display and no false inputs are registered.

Conclusion

This lab nearly meets excellence, although it is missing the criterion where if two buttons are pressed and one is released, the second button press is registered.

There are also the following known issues:

  1. Reset still trips the debounce high for some reason.
  2. Needs to be manually reset upon startup.
  3. Can’t press zero twice for some reason.
  4. The debounce_low fail criterion doesn’t actually really work, although in hardware testing this was revealed to be unnecessary.
  5. There’s a huge amount of pickup noise in the circuit which mostly goes away when earth grounded by an oscilloscope.

I spent about 35 hours working on this lab.

AI Prototype Summary

The monolithic prompt was certainly much more brief and was lacking certain necessary functions such as a debouncer. Both attempts synthesized immediately, although the decomposed prompt interestingly provided two approaches to solving the problem which halted synthesis until I commented out one of the options. Both modularized effectively, except the aforementioned missing functions.

There were all kinds of neat SystemVerilog tricks I didn’t know about, such as the $clog2() function which the number of bits needed to represent a number, or the ~| bitwise operator for reading whether any of the rows were true. I also especially like how the 7-seg decoder was laid out with a nice ASCII graphic of the 7 segments and using hex rather than binary for the case states. I also liked how the decomposed prompt separated the row + column combinations into a queryable table, which seemed like a logical way of decoding the result.

Both prompts were liable to create undriven connections and were definitely not usable without user-inputted debugging. I don’t like how both prompts read the row inputs in a non-one-hot manner, and the monolithic prompt didn’t even try decoding the input. The decomposed prompt did attempt this, but couldn’t have done it correctly without a specific keypad spec. I also did not like how the decomposed prompt handled the debouncer by simply waiting for a counter period, without actually checking if the input was steady.

In the future, I’ll definitely try a decomposed approach, especially because it encourages me, the prompter, to be much more specific with my request and thereby improves the result. It also helps you as the designer to think about what exactly does your code need to implement when you go and write it yourself. Especially because I don’t like immediately copying code from LLMs, but rather using them as example code to build my design around so I can think of each line of code as I write it. I also find LLMs much more useful for debugging, which we didn’t handle here.
